# Backend request interface

Next.js serves the backend at `/api`; the homepage reads published announcements and club information through the same content operations. Feature operations live under `src/` and take the internal actor ID only from `getCurrentUser`. They are server modules, never browser RPCs. SQL migrations remain the model source of truth.

Responses are `{ data: ... }` or `{ error: { code, message, requestId, fields? } }`. All API reads use `Cache-Control: no-store, private`; attendance is never served from a shared cache. Errors distinguish unauthenticated (401), denied (403), missing/hidden record (404), stale/duplicate change (409), invalid data (400/422), oversized upload (413), and infrastructure failure (503). Internal SQL/provider errors are not returned. Server failure logs contain a request ID, error type and code, without payloads or tokens.

Every mutation requires the exact `APP_URL` Origin; request bodies use JSON content type. Requests use same-origin credentials. A future form should keep the returned integer `revision` and send it on edits; a conflict requires a reload/review, not a silent retry overwriting newer data. Acceptance is deliberately retry-safe after success, returning the original membership.

## Applicant submission and recovery

`POST /api/me/applications` accepts an optional UUID `requestId` alongside the existing answers. The Apply interface generates it once for a logical submission and retains it with the validated answers in memory. The ID becomes that application's primary key. An unchanged retry by the same verified identity returns `201` with the original ID and the application's **current** status and submission timestamp, including after review or withdrawal. This differs from content creation's immutable response receipts. Changed effective answers or another actor using an existing ID receive `409`; a genuinely new application needs a new ID. Existing callers without an ID retain the original create behavior. Disabled accounts cannot replay submissions.

After an uncertain outcome, first read `/api/me/applications/entry` and look for the retained ID. If absent, an explicit retry uses the same ID and answers. Do not clear answers on a failed or timed-out save. The form freezes its submitted answers while recovery is pending; it does not automatically retry POSTs. A reload loses the unsaved in-memory draft and ID; the owner read still finds committed applications. No answers are stored in persistent browser storage.

The entry read shares `applications.submission_blocker` with the database insertion guard. `blockedBy` distinguishes an open application, a current active/paused membership, a separate restriction, and missing verified identity. No blocker does not imply an academic year is configured: `academicYear: null` independently prevents the frontend from offering submission. Withdrawal uses the loaded record ID and revision; a conflict requires a fresh read. A status refresh invalidates a withdrawal confirmation if that record's revision changed.

All `POST /api/admin/content/*` creates require a UUID `requestId` in the JSON body, including club-info and standalone images. Generate it with `crypto.randomUUID()` once when starting a logical save. Retain that ID together with the submitted fields and selected image bytes until the result is known; use the same ID and payload after a timeout, lost response, or retry. Generate a new ID for a separate creation or changed payload, even when its title/date matches another Story. PUT edits keep their revision contract and need no requestId.

Replay IDs are scoped to the authenticated actor and operation. An identical retry returns `201` with the original JSON result (including its original ID, image ID, revision and timestamps), even if that content has subsequently been edited. Use GET to load the current record. A valid but different payload under an already committed ID returns `409 CONFLICT`; fingerprints cover validated fields plus upload MIME, alt text and a hash of the actual bytes. Object-key order and schema defaults do not change the fingerprint. A failed validation or rolled-back transaction consumes no ID, so a corrected retry can use it; once committed, changed input requires a new ID. Permissions are rechecked for every retry. Do not automatically discard receipts: they preserve replay safety across process restarts and database restoration.

Content inputs are defined in `src/content/input.ts`. Stories require title/date, allow no description, and optionally reference an existing image. Resource links default to unpublished and require an explicit `published: true` admin edit before appearing publicly. A Story or announcement Save can include `upload: {base64, mimeType, altText}`; omit imageId when uploading. Image and content writes share a transaction. A failed save leaves no orphan upload; keep the selected file and user edits in frontend state so retry is possible. Allowed raster types: JPEG, PNG, WebP, GIF; up to 2 MiB encoded bytes, 16,777,216 decoded pixels and 8192 per side. Corrupt data and mismatched MIME are rejected by full decoding. Image bytes stay in PostgreSQL.

Session times are Tokyo local `YYYY-MM-DD` and `HH:mm`. Ranges use exclusive ends. Materials accept specific HTTPS Google Drive folder links, including account-index links. An absent link means materials are not added. Saving a link does not verify its contents or grant Drive access; admins must attach only reviewed materials folders. This backend uses no Drive credentials or API.

Published story and announcement responses include optional image alt text and dimensions (`image_alt`, `image_width`, `image_height`). They do not include image bytes or uploader identity; render images through the authorized public image route.

## Attendance selection and edits

Read and write `/admin/sessions/:id/attendance` with the selected session's ID. The response repeats `sessionId`; reject a response if it no longer matches the active selection. Abort old requests or track a request sequence. Reset selection-local roster and modal state when the selected session changes. The legacy code's old URL-only selection could retain the previous roster in React state; that is separate from backend caching. The new request tests cover A → B reads and save → reread, not the future UI interaction.

The roster uses membership state on that session's Tokyo date. Existing out-of-period attendance remains visible with `eligible: false` and can be corrected, but no new out-of-period record can be added. Cancellation preserves records and excludes them from percentages. Paused/pre-join periods and pending/excused marks follow the existing eligibility/percentage policy. Attendance edits lock the session and compare its revision, preventing competing batches from silently overwriting each other.

## Authentication and configuration

Protected member pages are `/dashboard`, `/dashboard/sessions/:id`, and `/dashboard/attendance`. `/members` remains the public people introduction. The dashboard defaults to the current Tokyo academic year and term, retains year/term/view in its URL, and switches session reads through the existing `/api/sessions` filters. Aborted or superseded reads cannot replace a newer selection. Server operations retain the active/paused/former policy. Attendance percentages come from `getOwnAttendanceSummary`, across all eligible history, independently of the session browser's filters. The compact dashboard shows up to three attendance records and three notices; the records page shows the full owner-visible history. Missing member cards, no eligible records, unsettled attendance, 0%, unavailable data, unconfigured calendars and empty terms have separate states.

Absence creation also accepts an optional UUID `requestId`. The browser retains it with the effective reason and session/date until the outcome is known. It becomes the notice ID; an unchanged verified-owner retry returns that notice's current status/revision, including after cancellation. Changed input or another member reusing the ID returns `409`. Requests without an ID retain the existing behavior. A genuinely new notice gets a new ID. The existing one-live-notice-per-member/session constraint still applies; no new date-only restriction is introduced. After an uncertain outcome the UI checks own notices, then offers an explicit same-ID retry. Unsaved reasons are kept in memory only. Cancellation uses the captured notice ID and revision, and refreshes the owner read after success or a conflict. Neither notice submission, acknowledgement nor cancellation changes final attendance automatically.

Use the single Neon Managed Better Auth SDK integration. The browser should use `createAuthClient()` from `@neondatabase/auth/next`, then `signIn.social({provider: "google", callbackURL: "/auth/complete"})`, `getSession()` and `signOut()`. The SDK proxy on `/auth/complete` exchanges the OAuth verifier; the completion route associates the stable internal identity. The auth proxy exposes only Google sign-in/linking, session lookup and sign-out. The application accepts neither email/password-only sessions nor client-supplied roles/identity IDs.

The Sign-in panel uses the SDK for Google sign-in and sign-out, and `/api/account` for fresh application access state. It does not derive authorization from a browser SDK session. `/auth/complete` verifies identity through `getCurrentUser`, then returns a private, uncached 303 redirect. `returnTo` accepts an internal path only; available public routes are explicitly listed in `src/auth/navigation.ts`. `/apply` is also an available destination after verified sign-in, with its own owner-only reads and eligibility states. Dashboard routes require effective member/admin access. Auth, API, unknown and unfinished protected destinations fall back to the account panel. Leadership controls link to `/admin` for effective admins only. Protected leadership routes recheck the same current-user verifier; API operations also enforce admin authorization. Session state is rechecked on mount, history restoration and tab focus. No application answers are stored in persistent browser storage. Real Google OAuth, account linking and hosted session restoration remain verification-pending.

`getCurrentUser` validates a fresh hosted session (bypassing SDK cookie cache), reads the linked Google provider account and checks enabled school identity/roles on every request. Initial association or email change requires a Google-signed ID token with the exact configured audience, valid issuer/expiry, verified school email and hosted domain. Later sessions must still match the stored Google subject and email. Multiple Google links, conflicting identities, or ambiguous imported emails require reconciliation; no records are silently merged. Provider tables are read only. The verified club account receives an explicit audited admin grant; leaders must receive an explicit admin grant separately.

Set `APP_URL`, pooled runtime `DATABASE_URL`, branch `NEON_AUTH_BASE_URL`, locally generated `NEON_AUTH_COOKIE_SECRET` (32+ characters), and the exact `GOOGLE_OAUTH_CLIENT_ID`. Keep environment values outside Git. Never use old connector/CLI identity as evidence of deployed credentials. Deployments need their own correctly scoped variables, hosted trusted origin, and configured Google OAuth client settings. The temporary ownership arrangement and required migration are described below. Run migrations as owner with a direct URL; after hosted Auth exists, apply `db/runtime-role.sql` and grant the `logos_runtime` group to a dedicated application login. Reapply grants after migrations add new relations/functions. Tests exercise request operations under this non-owner group and verify it cannot mutate Auth or create tables.

## Public homepage session summary

Admin access requires an explicit `people.role_grants` record for every account, including the club mailbox. Signing in never creates or restores a role grant. Existing grants are unaffected by identity association.

The server-rendered homepage also calls `getPublicSessionSummary` in `src/sessions/public.ts`. It returns only the latest completed, non-cancelled session’s title and description, plus every non-cancelled session title in the current Tokyo term in chronological order. An unconfigured term (`null`), an empty programme (`[]`), and an unavailable read are distinct states. This is a narrow public projection of the same session records; authenticated calendar endpoints retain their existing permissions and full session details. No materials, location, attendance, identity, or administrative fields are returned.

## Leadership interfaces and recurring meetings

`/admin` is the focused tool list. Applications, members, sessions/attendance, public content, and recurring meeting settings have separate destinations under it. Private reads and mutations use the existing operations, no-store responses, loaded revisions, and same-origin requests. Application queue reads accept a numeric `offset` in pages of 50. Member detail adds stored attendance links and dated membership periods, restricted to admins.

`GET, PUT /api/admin/recurring-meeting` loads/saves the central singleton. PUT accepts `{revision, weekday, startTime, durationMinutes, room, published}`. Weekday is Sunday=0 through Saturday=6; time is Tokyo `HH:mm`; duration is 1-1440 minutes; room is optional, up to 120 characters. A missing singleton uses revision 0 for the first save, defaults to withheld, and concurrent/stale saves return 409. Changes are audited. Apply migration `0009_recurring_meeting.sql` and reapply runtime grants on the verified target before using this operation.

`GET /api/public/recurring-meeting` returns null when missing/withheld, otherwise only `{weekday,startTime,durationMinutes,room}`. Home and Meetings consume this projection dynamically. Publishing and withholding act on all four fields together. No identities, notes, attendance, materials or revisions enter the public projection. Existing sessions are never changed by recurring settings. New session forms offer an explicit action to copy the start time and duration; the session date must still be chosen.

Leadership profile saves now optionally accept the same validated inline image upload as stories and announcements, with atomic attachment and byte-aware replay fingerprints. Existing no-upload leadership creation receipts retain their original fingerprint contract. Every content create keeps its exact requestId, effective payload and selected bytes in memory through uncertain recovery. Forms prevent edits during recovery and offer an explicit unchanged retry, or a deliberate changed submission with a new ID. Reload loses unsaved drafts; no private values or upload bytes are stored in persistent browser storage. Saving a published record changes the public website; unchecked publication saves a private draft. Club information is public when saved.

The local leadership harness uses synthetic identities and a disposable PostgreSQL database outside the repository. It is not an authentication bypass in the application. Real Google OAuth, existing-account reconciliation and hosted cookie/session restoration remain verification-pending; implementation and synthetic checks are not production readiness.
